> 대상: 분리배출 안내 챗봇 Ecobot (SKN32 4차, Django 이식본)
> 범위: BM25 하이브리드 검색 도입, 비용 지표 계측
> 기준: 3차 프로젝트 보고서 §8-3 「남은 과제」의 두 항목

## 1. 배경과 목표

3차 보고서는 다음 과제를 두 가지 남겼다.

| 항목 | 3차 상태 |

## 2. 테스트 계획

### 2-1. 왜 층을 나눠 재는가

3차에서 한 가지 관찰이 있었다. v6(Few-shot 예시 추가)이 답변 통과율을
76% → 80%로 올렸지만 **검색 정확도는 81.0% 그대로**였다. 프롬프트는 검색에
관여하지 않으므로 당연한 결과였고, 동시에 두 층을 나눠 재야 원인을 짚을 수
있다는 근거이기도 했다.

이번에는 반대 방향의 변경이다. 검색기를 바꿨으니 검색 지표는 오를 것이
예상되지만, 그것이 답변 품질로 이어지는지는 별도 문제다. 그래서 세 층을
독립적으로 측정했다.

| 층 | 재는 것 | 도구 | 정답 기준 |
|---|---|---|---|
| **L1 검색** | 관련 청크를 찾아오는가 | `evals/run_ir_eval.py` | 정답 chunk ID 매칭 |
| **L2 답변** | 근거로 제대로 답하는가 | `evals/run_eval_hybrid.py` (3차 원본) | LLM 심판 + 규칙 |
| **L3 비용** | 질문 1건에 얼마가 드는가 | `evals/run_search_eval.py` | API usage 필드 |

L2 도구는 3차 원본을 **본문 무수정**으로 이식했다. 측정 방법이 바뀌면 3차
지표와의 비교가 무효가 되기 때문이다(이식 근거는 `HANDOFF.md` §2-2, AST 비교로
본문 동일성 확인).

### 2-2. 비교 조건

`RAG_PIPELINE` 값 하나만 바꿔가며 동일 평가셋으로 3회 측정했다.

| 파이프라인 | 검색 방식 |
|---|---|
| `legacy` | dense 단독 (FAISS + 코사인 유사도) — 3차부터의 기본 경로 |
| `bm25` | sparse 단독 (BM25Okapi + 형태소 토크나이저) |
| `hybrid` | dense + BM25 를 RRF(Reciprocal Rank Fusion)로 융합 |

`legacy` 를 먼저 재는 것은 **이식 검증**이 목적이다. 이식이 정상임을 확인한
뒤에야 BM25 도입 효과를 논할 수 있다. 두 변화를 한 번에 섞으면 어느 쪽
효과인지 구분할 수 없다.

### 2-3. 평가셋

3차 30문항을 100문항으로 확장했다. **기존 q001~q030 은 원형 그대로 앞에 두어
동일 조건 비교가 가능하도록 했다.**

| 유형 | 문항 | 확인하는 것 |
|---|---|---|
| `single_fact` | 23 | 품목 판정 정확도 |
| `region_specific` | 58 | 선택한 지역 기준으로 답하는가 |
| `cross_reference` | 9 | 가이드와 법령을 함께 인용하는가 |
| `no_answer` | 10 | 자료 없는 질문에 지어내지 않는가 |

모범답안은 **`data/guide/` 의 실제 문서 내용에서 작성**했다. 외부 자료를 쓰면
코퍼스에 없는 사실이 정답이 되어 평가가 무의미해진다. 작성 후 전체 코퍼스와
대조해 근거 문서를 자동 검증했고, 이 과정에서 13문항의 `region` 이 잘못
지정된 것을 발견해 교정했다(예: "양파 껍질"은 공통 상식으로 보이지만 실제로는
서울시·천안시 문서에만 서술되어 있어, `region=common` 으로 두면 검색 대상에서
빠진다).

실험 장치 두 가지를 함께 넣었다.

- **지역 단서 대조군** (`region_explicit: false`, 6문항) — 같은 질문을 지역명이
  있는 버전과 없는 버전으로 만들어, 두 버전의 점수 차이로 지역 필터의 순수
  기여도를 잰다.
- **병렬군** (`parallel_group`, 12문항) — 같은 질문을 지역만 바꿔 던진다.
  음식물쓰레기 배출 방식은 제주가 RFID+티머니, 수원이 RFID+캐시비,
  대구·대전·울산이 전용용기+납부필증으로 실제로 갈리므로, 검색기가 지역을
  구분하는지 직접 확인할 수 있다.

### 2-4. 측정 환경

```
임베딩   OpenAI text-embedding-3-small (1536d)
LLM      gpt-4o-mini
임계값   RAG_MIN_SCORE = 0.36 (3차 확정값)
청킹     700자 / 100자 중첩, 법령은 조문 단위, 가이드는 섹션·품목 단위
코퍼스   문서 33개 / 청크 1,006개 (지역 10개 + 전국 공통 + 법령)
검색자리 지역 2 + 공통 1 + 법령 2
```

## 3. 측정 결과

### 3-1. L1 — 검색

| Pipeline | R@1 | R@3 | R@5 | MRR@5 | ms/query |
|---|---|---|---|---|---|
| legacy | 0.303 | 0.483 | 0.607 | 0.411 | (재측정 필요) |
| bm25 | 0.360 | 0.528 | 0.640 | 0.457 | 119 |
| hybrid | **0.360** | **0.629** | **0.730** | **0.497** | (재측정 필요) |

hybrid 가 모든 품질 지표에서 1위이며, 특히 R@3 에서 격차가 크다(0.528 → 0.629).
정답을 찾아오는 것뿐 아니라 **상위로 올리는 능력**에서 융합의 효과가 나타났다.

> **지연시간 미확정**: 측정 순서상 첫 번째로 실행된 `legacy` 가 임베딩 API
> 호출 비용을 단독으로 부담해, hybrid 가 legacy 를 포함하는데도 더 빠르게
> 측정되는 모순이 발생했다. 워밍업을 추가해 재측정이 필요하다. 현재 신뢰할 수
> 있는 값은 임베딩을 사용하지 않는 `bm25` 의 119ms 뿐이다.

### 3-3. L3 — 비용

질문 10건 표본, API 응답의 `usage` 필드를 그대로 적립한 값이다(추정 아님).

| | legacy | bm25 | hybrid |
|---|---|---|---|
| LLM 호출 | 9회 | 10회 | 10회 |
| 호출당 입력 토큰 | 2,990 | 3,270 | 3,094 |
| 호출당 출력 토큰 | 132 | 134 | 123 |
| 질의 임베딩 호출 | 1회 | **0회** | 1회 |

입력 토큰의 구성은 다음과 같다.

```
입력 3,100 토큰
```

`legacy` 의 LLM 호출이 9회인 것은 한 문항에서 근거를 전혀 찾지 못해 LLM 을
호출하지 않았기 때문이다. 환각 방지 로직이 LLM 호출 **이전**에 차단하므로
비용도 함께 절약된다.

## 4. 해석

### 4-1. 검색 1위와 답변 1위가 다르다

검색 R@5 는 hybrid(0.730)가 1위인데 답변 통과율은 bm25(94%)가 1위다. 이 역전이
층을 나눠 잰 이유를 그대로 증명한다.

오거부(답할 수 있는데 근거를 못 찾아 포기한 건)를 제외하고 보면 세 파이프라인의
**답변 시도 시 통과율은 93.3% / 95.9% / 95.8% 로 사실상 같다.** 통과율 차이는
답변 능력이 아니라 오거부 횟수(10 / 2 / 5)에서 발생했다.

> **검색 개선의 효과는 답변 품질 향상이 아니라 오거부 감소로 나타났다.**

legacy 의 실패 16건 중 10건이 오거부이며, 이는 검색 R@5 가 0.607 에 그친 것과
같은 사실의 다른 표현이다.

### 4-2. 환각과 오거부의 트레이드오프

| | 임계값 판정 기준 | 오거부 | 환각 |
|---|---|---|---|
| legacy | `vector_score ≥ 0.36` | 10 | 9 |
| hybrid | `vector_score ≥ 0.36` | 5 | **6** |
| bm25 | `bm25_score ≥ 0.0` (사실상 미적용) | **2** | 8 |

bm25 는 BM25 스케일 임계값이 확정되지 않아 사실상 필터가 꺼진 상태다. 그래서
거부를 덜 하고 통과율이 높은 대신, 근거가 약한 상태에서 답을 시도해 환각률이
8.0% 로 더 높다. hybrid 는 벡터 유사도로 판정하므로 보수적이고, 환각률 6.0% 로
셋 중 가장 낮으며 **3차의 6.7% 보다도 개선**됐다.

이 서비스의 핵심 요건이 환각 방지라는 점을 근거로, 통과율 3%p 대신 환각률
2%p 를 우선해 **hybrid 를 채택**했다.

### 4-3. 비용은 검색이 아니라 프롬프트가 결정한다

세 파이프라인의 비용 차이는 20% 이내이며, 그마저도 검색 방식이 아니라 가져온
근거 청크의 길이 차이다. 반면 입력 토큰의 68% 는 매 질문 반복되는 Few-shot
고정 프롬프트다.

3차에서 통과율을 76% → 80% 로 올린 그 예시들이 비용의 3분의 2 를 차지하고
있었다. 품질과 비용의 트레이드오프가 처음으로 숫자로 드러났다.

프롬프트 캐싱을 적용하면 고정부가 절반 가격이 되어 약 30% 절감이 가능하다
(고정부가 프롬프트 앞쪽에 있고 1,024 토큰을 넘어 조건을 만족한다).

또한 막연히 부담으로 여겼던 **질의 임베딩 비용은 전체의 0.07%** 에 불과했다.
bm25 는 질의 임베딩 호출이 0회이므로 금액상 이득은 미미하지만 외부 API 의존이
하나 줄어든다.

## 5. 측정 과정에서 발견한 결함

3차 보고서 §6 과 같은 성격의 목록이다. **모두 에러 없이 조용히 지나갈 수 있었던
문제**다.

| 결함 | 영향 | 발견 경로 |
|---|---|---|
| **RRF 점수를 임계값에 그대로 사용** | hybrid 가 모든 질문에 "자료 없음" 반환 | hybrid 검색 결과 0건 |
| BM25 토크나이저가 조사를 분리하지 않음 | "종이컵은" ≠ "종이컵을" 로 핵심 명사 미매칭 | BM25 R@5 가 legacy 수준에 정체 |
| 지역 문서 4건이 `region=common` 으로 색인 | 지역 필터가 해당 지역을 걸러내지 못함 | 평가셋 정합성 검사 |
| 평가 스크립트가 `_retrieve()` 를 직접 호출 | 지역 필터·임계값·자리배분이 측정에서 누락 | L1/L2 수치 불일치 |
| `no_answer` 문항이 recall 분모에 포함 | R@5 상한이 구조적으로 막힘 | 지표 상한 계산 |

### 5-1. RRF 점수 스케일 (가장 중요)

`search()` 의 환각 방지 1차 장치는 원래 한 줄이었다.

```python
results = [r for r in results if r.get("score", 0.0) >= min_score]
```

파이프라인이 하나일 때는 `score` 가 항상 코사인 유사도(0~1)였으므로 문제가
없었다. BM25 와 hybrid 가 들어오면서 **같은 필드에 서로 다른 스케일의 숫자**가
담기게 됐다.

| 파이프라인 | score 범위 | `MIN_SCORE=0.36` 적용 시 |
|---|---|---|
| legacy | 코사인 0 ~ 1 | 정상 |
| bm25 | BM25 raw 0 ~ 상한없음 | 아무것도 못 거름 → 환각 방지 무력화 |
| hybrid | RRF 0 ~ 2/(K+1) = **0.0328** | 전부 탈락 → 모든 질문에 "자료 없음" |

RRF 의 이론상 최댓값이 0.0328 이므로 0.36 과 비교하면 남는 결과가 없고,
`ask()` 는 근거 0건이면 LLM 을 호출하지 않는다. 즉 **hybrid 로 배포하면 챗봇이
아무 답도 하지 못하는데 에러는 나지 않는다.**

RRF 를 0~1 로 정규화하는 것은 해결책이 아니다. RRF 는 순위 기반이므로 무관한
질문에서도 1위 문서는 최댓값 근처를 받는다. 정규화하면 그 값이 1.0 이 되어 어떤
임계값도 통과한다 — **장애가 환각으로 바뀔 뿐이다.**

따라서 hybrid 는 융합 점수가 아니라 **융합 전 원점수**(`vector_score` /
`bm25_score`)로 판정하도록 분리했다(`rag/scoring.py`).

### 5-2. 한국어 BM25 는 토크나이저가 전제다

`rank_bm25` 를 붙이는 것만으로는 효과가 없었다.

```
질의 "종이컵은 어떻게 버려요?"  →  ['종이컵은', '어떻게', '버려요']
문서 "종이컵을 헹군 뒤 배출"     →  ['종이컵을', '헹군', '배출']
```

BM25 는 정확한 단어 일치가 전부이므로 조사가 붙은 채로는 핵심 명사가 매칭되지
않는다. 형태소 분석기(kiwipiepy)를 도입해 조사·어미를 분리하고, 도메인 복합명사
(`음식물쓰레기` → `음식물`, `쓰레기`)를 함께 색인하도록 한 뒤에야 성능이 나왔다.
법령은 "음식물류 폐기물", 가이드는 "음식물쓰레기"로 표기가 갈리기 때문이다.

## 6. 한계와 미검증 항목

발표 시 함께 밝혀야 할 사항이다.

| 항목 | 내용 |
|---|---|
| **L1 정답셋(gold)이 자동 생성** | 모범답안과의 어휘 중첩으로 정답 청크를 추정했다. 사실상 소박한 lexical retriever 이므로 **어휘 매칭 계열(bm25/hybrid)에 유리한 편향**이 있다. L1 수치는 상대 비교용으로만 해석해야 한다. |
| **지연시간 미확정** | 워밍업 부재로 측정 순서가 값에 영향을 줬다. 재측정 필요. |
| **통계적 유의성 미산출** | R@5 에서 bm25 0.640 vs hybrid 0.730 은 문항 약 8건 차이다. n=100 기준 신뢰구간이 겹칠 수 있어 McNemar 검정이 필요하다. |
| **동일 30문항 재집계 미완** | 100문항 84% 와 3차 30문항 93.3% 를 직접 비교할 수 없다. q001~q030 부분집합 집계로 해소 가능. |
| **BM25 임계값 미확정** | `RAG_MIN_SCORE_BM25 = 0.0` 은 사실상 무필터다. no_answer 문항의 BM25 점수가 answerable 문항과 겹쳐 단일 임계값으로 분리되지 않을 가능성이 있다. |
| **문서 단위 region 태깅의 한계** | 전국 공통 가이드 안에 지자체별로 갈리는 내용이 섞여 있다. 문서 단위로만 태그를 붙이는 구조라 청크 단위 태깅이 필요하다. |

## 7. 결론

| 항목 | 결과 |
|---|---|
| BM25 하이브리드 검색 | **적용 완료.** R@5 0.607 → 0.730 (+20%) |
| 비용 지표 | **계측 완료.** 질문당 $0.00054, 1,000건당 $0.54 |
| 채택 파이프라인 | **hybrid** (환각률 6.0%, 3차 6.7% 대비 개선) |

세 가지를 확인했다.

1. **검색 개선의 효과는 답변 품질이 아니라 오거부 감소로 나타난다.** 근거를
   찾아오기만 하면 답변 품질은 파이프라인과 무관하게 96% 수준으로 같다.
2. **통과율 1위와 안전성 1위는 다르다.** 임계값이 꺼진 파이프라인은 통과율이
   높아 보이지만 환각률이 함께 오른다.
3. **비용은 검색 방식이 아니라 프롬프트 길이가 결정한다.** 품질을 위해 추가한
   Few-shot 예시가 비용의 68% 를 차지한다.

## 8. 다음 과제

| 우선순위 | 항목 | 근거 |
|---|---|---|
| 1 | 동일 30문항 재집계 + 지연시간 재측정 | 위 §6 의 미검증 항목 해소 |
| 2 | `RAG_MIN_SCORE_BM25` 확정 | 환각 방지 1차 장치 복구 |
| 3 | Cross-encoder 리랭커 | R@1 0.360 vs R@5 0.730 — 정답은 찾았으나 상위로 못 올린 구간이 크다 |
| 4 | 프롬프트 캐싱 | 비용 약 30% 절감 가능 |
| 5 | 청크 단위 region 태깅 | 공통 가이드 내 지역별 내용 분리 |
| 6 | `cross_reference` 유형 개선 | hybrid 에서만 66.7% 로 정체 (9문항, 표본 부족) |

3번은 이번 측정으로 근거가 확보된 항목이다. R@1 0.360 과 R@5 0.730 의 격차는
**정답 문서가 이미 검색되고 있으나 순위를 못 매기고 있다**는 뜻이며, 리랭커의
전형적인 적용 지점이다.

## 부록. 재현 방법

```bash
# 환경 검증
python evals/check_setup.py

# 문서 적재 · 색인 (FAISS + BM25)
python manage.py seed_docs --reindex

# 평가셋 정합성
python evals/validate_eval_set.py

# L1 검색
python evals/build_gold_chunks.py
python evals/run_ir_eval.py

# L2 답변 (파이프라인별로 3회)
set RAG_PIPELINE=legacy && python -m evals.run_eval_hybrid
set RAG_PIPELINE=bm25   && python -m evals.run_eval_hybrid
set RAG_PIPELINE=hybrid && python -m evals.run_eval_hybrid
python -m evals.run_report

# L3 비용
python -m evals.run_search_eval --cost-sample 10 --index-cost
```

측정 원본은 `evals/results_*.json`, `evals/ir_eval_*.json`,
`evals/search_eval_results.json`, `threshold_*.json` 에 날짜별로 저장된다.
