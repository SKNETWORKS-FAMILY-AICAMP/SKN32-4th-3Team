# 0001. ecobotapt.com 배포 구성

- 상태: 채택
- 날짜: 2026-08-26
- 맥락: 기존 Caddy가 `기존-사이트.example.com`(Next.js)을 서빙 중인 자택 서버에
  EcoBot을 두 번째 사이트로 얹는다.

## 결정 1 — 정적 파일은 Caddy가 아니라 WhiteNoise가 서빙한다

**왜 자명하지 않은가:** 앞단에 웹서버가 있으면 정적 파일은 그쪽이 직접
내보내는 것이 정석이다. 여기서는 그렇게 하지 않았다.

Caddy는 `caddy` 사용자(uid 997)로 돌고, 프로젝트는 `<앱계정 홈>`(**0750**,
소유 `앱계정:앱계정`) 아래에 있다. `caddy`는 이 디렉터리를 **통과조차 하지
못한다.** `root * $PROJECT_DIR/staticfiles`를 써도 403이 난다.

**검토했다가 안 쓴 대안:**

| 대안 | 왜 안 썼나 |
|---|---|
| `chmod 755 <앱계정 홈>` | 홈 전체를 다른 로컬 사용자에게 여는 대가가 정적 파일 몇 개보다 크다 |
| `setfacl -m u:caddy:x <앱계정 홈>` | 동작은 한다. 다만 ACL은 `ls -l`에 드러나지 않아, 나중에 홈을 옮기거나 권한을 손보는 사람이 이유를 모른 채 깨뜨린다 |
| `staticfiles/`를 `/var/www`로 복사 | `collectstatic` 뒤에 복사 단계가 하나 더 붙고, 두 위치가 어긋나면 낡은 CSS가 서빙된다 |

**대가:** 정적 파일이 파이썬 프로세스를 거친다. WhiteNoise는 파일을 메모리에
올려두고 gzip/brotli 사본을 미리 만들어 두므로 실측 부담은 작고, 해시된
파일명에 `immutable` 캐시 헤더가 붙어 재요청 자체가 드물다. 이 규모에서는
gunicorn 워커를 붙잡는 비용보다 경로 결합이 없는 이점이 크다.

**같은 제약이 배포 절차에도 걸린다.** sudo 를 가진 계정은 `관리 계정`(uid
1000) 하나뿐인데, 이 계정 역시 `<앱계정 홈>` 를 통과하지 못한다. 그래서

```bash
sudo tee -a /etc/caddy/Caddyfile < <앱계정 홈>/.../Caddyfile.ecobotapt
```

가 실패한다 — **리다이렉트는 sudo 가 아니라 셸이 수행**하므로 파일을 여는
주체가 여전히 `관리 계정` 다. `sudo` 를 붙였는데 Permission denied 가 나서
원인을 엉뚱한 데서 찾기 쉬운 형태라, root 로 도는 `deploy/install-system.sh`
로 감싸고 런북 맨 앞에 계정 구조 절을 두었다.

## 결정 2 — 업로드 파일(media)은 Django가 서빙한다

같은 권한 문제다. `django.views.static.serve`는 경로 탈출을 막아 주지만 파일을
파이썬으로 읽어 내보내므로 느리다. 이 프로젝트의 업로드는 프로필 사진·게시글
첨부·단지 규정 PDF 수준이라 실사용에 문제가 없다고 판단했다.

**함정:** `django.conf.urls.static.static()`은 `DEBUG=False`이면 **빈 리스트를
반환한다.** 기존 `config/urls.py`는 이 함수만 쓰고 있어서, 그대로 배포하면
업로드 파일이 전부 404가 되는데 **에러 로그에는 아무것도 안 남는다.**
`re_path` + `static_serve`로 명시적으로 갈아끼웠다.

**빠져나갈 길:** `DJANGO_MEDIA_ROOT`를 홈 밖(`/var/www/ecobot/media`)으로
돌리고 `DJANGO_SERVE_MEDIA=False`로 끄면 Caddy `file_server`로 넘어간다.
설정 두 줄이라 나중에 트래픽이 늘면 바꿀 수 있다.

## 결정 3 — 운영 의존성에서 torch 계열을 뺀다

`requirements-prod.txt`는 `sentence-transformers`와 `langchain-*`을 뺐다.
전자가 끌고 오는 torch만 2~3GB다. **실측: venv 238MB(uv) / 307MB(pip)** — 포함 시 3GB 이상.

안전한 이유는 두 묶음 모두 **함수 안에서 지연 임포트**되기 때문이다
(`rag/embeddings.py:49`, `rag/service.py:153`, `rag/vector_store.py:161`).
모듈 최상단 임포트는 `TYPE_CHECKING` 가드 안에 있어 런타임에 실행되지 않는다.

**대가 — 이게 진짜 비용이다:** `.env`와 requirements 파일이 **암묵적으로
결합**된다. 누가 `EMBEDDING_BACKEND=local`이나 `RAG_PIPELINE=langchain`으로
바꾸면 기동은 정상인데 **그 요청에서만** `ModuleNotFoundError`가 난다.
기동 시점 검증에 걸리지 않는 종류의 실패라, 두 파일 양쪽에 경고를 남겼다.

## 결정 4 — gunicorn `timeout = 180`, `worker_class = gthread`

기본값 30초로는 부족하다. 문서 업로드가 **그 요청 안에서**
`rebuild_index()`로 전체 문서를 재임베딩한다(`rag/views.py:167`). 30초를
넘기면 워커가 죽어 업로드는 500으로 끝나고 인덱스는 중간 상태로 남는다.

워커형을 스레드로 잡은 것은 이 앱의 요청이 CPU가 아니라 **대기**(OpenAI
호출)가 대부분이기 때문이다. 동기 워커면 대기 중인 요청이 프로세스를 통째로
붙잡는다.

**Caddy 쪽에도 같은 180초를 넣었다.** 한쪽만 늘리면 짧은 쪽에서 끊긴다 —
두 곳에 흩어진 값이라 다음 사람이 한쪽만 보고 고칠 위험이 있어 양쪽 주석에
서로를 가리키게 적었다.

**제대로 된 해법은 재색인을 백그라운드 작업으로 빼는 것**이다. 타임아웃 상향은
그 전까지의 임시방편이다.

## 결정 5 — `CSRF_TRUSTED_ORIGINS`를 `ALLOWED_HOSTS`에서 유도한다

명시하지 않으면 `ALLOWED_HOSTS`의 실제 도메인에서 `https://` 형태로 만든다.
도메인을 추가할 때 두 곳을 고치다 한 곳을 빠뜨리는 사고가 잦고, 그 증상이
"로그인 버튼을 누르면 403"이라 원인에서 먼 곳에 나타나기 때문이다.
`DJANGO_CSRF_TRUSTED_ORIGINS`로 언제든 덮어쓸 수 있다.

## 결정 6 — `mysqlclient` 를 유지하고 빌드 의존성을 감수한다

배포 준비 중 `python3.12-venv` 가 없어 venv 가 pip 없이 만들어지는 문제를
겪었다. uv 로 갈아타면 이 apt 의존성이 사라진다 — **그리고 실제로 사라졌다.**
uv 는 ensurepip 없이 venv 를 만들고 없는 파이썬 버전은 직접 내려받는다.

**그런데 `mysqlclient` 는 uv 로도 해결되지 않았다.** PyPI 에 올라온 휠이
**`win_amd64` 하나뿐**이다(2.2.8 기준). Linux·macOS 는 소스 빌드가 강제되고,
MySQL 클라이언트 헤더가 없으면 이렇게 죽는다:

```
Exception: Can not find valid pkg-config name.
```

즉 uv 는 **두 apt 패키지 중 하나만** 없애 준다. 이걸 몰라서 "uv 쓰면 apt 안
건드려도 되겠지"로 넘어가면 서버에서 같은 자리에 다시 걸린다.

**검토했다가 안 쓴 대안:**

| 대안 | 왜 안 썼나 |
|---|---|
| `PyMySQL` (순수 파이썬) | 빌드 의존성이 사라지지만 Django 가 공식 지원하는 드라이버가 아니다. `install_as_MySQLdb()` 몽키패치가 필요하고, 드라이버를 바꾸는 위험이 apt 한 줄보다 크다 |
| `mysql-connector-python` | 같은 이유. 게다가 Django 백엔드가 Oracle 배포판에 묶인다 |
| 개발도 전부 SQLite | 운영이 MySQL 인데 개발이 SQLite 면 그 차이가 배포 시점에 드러난다 |

**대가:** 새 팀원이 Linux·macOS 에서 합류할 때마다 빌드 의존성 한 줄을 깔아야
한다. Windows 는 휠이 있어 영향이 없고, 개발 중 MySQL 이 필요 없으면
`DB_ENGINE=sqlite3` 으로 우회된다. README 에 환경별 표를 넣어 두었다.

## 결정 7 — 파이썬은 3.10~3.13 을 모두 지원한다

3.12 로 못 박지 않았다. 팀원 환경이 3.11 인 경우가 있어서다.
**3.11.14 와 3.12.3 에서 색인·기동까지 실제로 검증**했다(문서 25개 → 청크 880개).
3.12 전용 문법(PEP 695 타입 파라미터, `itertools.batched`, `@override`)은
쓰지 않는다. 3.9 이하는 이식 코드의 `str | None` 때문에 불가하다.

`.python-version` 은 3.12 로 남겨 두었다. uv·pyenv 가 이 파일을 보고 없는
버전을 자동으로 맞춰 주므로, 지우는 것보다 두는 편이 버전이 갈리지 않는다.

## 결정 8 — 재색인을 요청 밖으로 뺀다 (2026-08-26 추가)

결정 4 에서 "제대로 된 해법은 재색인을 백그라운드로 빼는 것이고 타임아웃
상향은 그 전까지의 임시방편"이라고 적어 두었다. 그걸 처리했다.

```
웹 요청 → dirty=True + 트리거 파일 touch → 즉시 반환 (실측 16ms)
                     │
            systemd path 유닛이 감지
                     ▼
     manage.py rag_reindex --if-needed  (ecobot-reindex.service)
```

**검토했다가 안 쓴 대안:**

| 대안 | 왜 안 썼나 |
|---|---|
| Celery / RQ | 브로커(Redis)를 하나 더 띄워야 한다. 이 프로젝트의 비동기 작업은 이것 하나뿐이라 운영 대상이 늘어나는 값이 크다. 작업 종류가 늘면 그때 옮기는 게 맞다 |
| `threading.Thread` | 워커가 `max_requests` 로 재시작하면 진행 중인 스레드가 함께 죽는다. 실패한 사실도 남지 않는다 |
| 웹 프로세스에서 `subprocess.Popen` | 고아 프로세스 관리와 로그 수집을 직접 해야 한다. systemd 는 둘 다 공짜로 해 준다 |
| 타이머만 (path 유닛 없이) | 최대 5분 지연. 문서를 올린 관리자가 "반영이 안 된다"고 판단하기에 충분한 시간이다 |

**동시 실행은 flock 으로 막는다.** DB 플래그로 흉내 내지 않은 이유는,
프로세스가 죽으면 `status=running` 이 영구히 남아 이후 실행이 전부 막히기
때문이다. flock 은 프로세스가 사라지면 커널이 푼다.

**대가 — 삭제가 즉시 반영되지 않는다.** 문서를 지워도 재색인 전까지 청크가
인덱스에 남는다. 그 사이의 질문이 삭제된 문서를 인용하면 3차 트러블슈팅
4번이 그대로 재현된다. 그래서 `search()` 가 DB 에 없거나 승인 상태가 아닌
`document_id` 를 결과에서 걸러낸다(`_drop_missing_documents`). 검색마다
DB 조회가 한 번 늘지만, 결과가 임계값을 통과한 뒤(가장 적을 때) 걸러서
대상이 보통 4~5건이다.

## 결정 9 — 챗봇에 하루 한도를 둔다 (2026-08-26 추가)

`CHAT_DAILY_LIMIT`(기본 50). 회원가입이 열려 있고 질문마다 임베딩 + LLM
호출이 나가므로, 계정 하나로 API 비용을 무제한 태울 수 있었다.

OpenAI 대시보드의 월 한도는 **"터지기 직전에 서비스 전체를 멈추는"
차단기**다. 그것만 두면 한 명이 예산을 다 쓰고 나머지 사용자가 전부 막힌다.
둘은 대체재가 아니라 층이 다르다.

**왜 캐시가 아니라 DB 로 세는가:** gunicorn 워커가 3개인데 Django 기본
캐시(locmem)는 프로세스마다 따로다. 캐시로 세면 실효 한도가 3배가 되고,
워커 수를 바꿀 때마다 조용히 달라진다 — 설정값과 실제 동작이 어긋나는데
아무 데도 안 나타나는 종류의 버그다. `ChatLog` 는 이미 질문마다 한 행씩
쌓이고 `created_at` 에 인덱스가 있다.

**대가:** 질문마다 COUNT 쿼리가 한 번 는다. LLM 호출 한 번 앞에서는
무시할 만하고, Redis 를 붙이면 캐시로 옮길 수 있다.

한도 검사는 **다른 어떤 작업보다 먼저** 한다. 대화방을 만들거나 질문을
저장한 뒤에 막으면 답변 없는 질문만 기록에 남는다.

## 결정 10 — MySQL 을 로컬로 묶고, DDNS 는 systemd 로 돌린다 (2026-08-26 추가)

**MySQL.** Ubuntu 기본 설정은 `bind-address` 가 주석 처리돼 있어 `*:3306`
으로 열린다. 공유기가 포워딩하지 않아 인터넷에서는 안 닿았지만 LAN 에서는
접속됐다. `127.0.0.1` 로 묶었다. 잠그기 전에 로컬 외 연결이 있는지 확인하고
있으면 중단하게 했다 — 그대로 재시작하면 그쪽이 말없이 끊긴다.
`ecobot` 은 재시작하지 않아도 됐다(`CONN_MAX_AGE=0` 이라 요청마다 새 연결).

**DDNS.** 가정 회선이라 공인 IP 가 고정이 아니고, 바뀌면 `ecobotapt.com` 과
`기존-사이트.example.com` 이 **함께** 죽는다. 두 도메인은 zone 이 다르지만 같은
Cloudflare 계정이라 토큰 하나로 처리된다.

조용히 망가지는 경로 셋을 막았다 — 셋 다 "동작하는 것처럼 보이는데 틀린"
종류다:

| 막은 것 | 안 막으면 |
|---|---|
| IP 조회처 3곳 + 형식 검증 | 조회처가 죽었을 때 빈 값으로 A 레코드를 덮어써 도메인이 통째로 날아간다 |
| `proxied`·`ttl` 을 원래 값 그대로 전송 | Cloudflare 가 기본값으로 되돌려 회색 구름이 주황 구름이 되고, **Caddy 의 인증서 갱신이 막힌다** |
| 시작 시 토큰 검증 | 토큰이 틀리면 모든 조회가 빈 결과라 "zone 을 찾지 못했습니다"로 보인다. 원인에서 먼 곳(Cloudflare zone 설정)을 뒤지게 된다 |

세 번째는 실제로 겪고 고쳤다. 가짜 토큰으로 돌렸더니 zone 문제로 보였다.

**대가:** 토큰이 서버에 평문으로 남는다(`/etc/ddns-cloudflare/config.env`,
0600 root). zone 두 개의 DNS 편집 권한뿐이라 유출 시 피해 범위는 좁지만,
0 은 아니다.

## 결정 11 — 업로드 파일의 수명을 레코드에 맞춘다 (2026-08-26 추가)

배포 검증 중 발견했다. Django 의 `FileField` 는 레코드를 지워도 파일을
지우지 않는다(1.3 에서 의도적으로 바뀐 동작 — 트랜잭션 롤백 시 파일을
되살릴 수 없어서). 이 프로젝트에는 그 뒤처리가 없어서, **문서를 지울 때마다
`media/` 에 고아 파일이 쌓여 왔다.** 재색인 비동기화와 무관한, 원래부터
있던 문제다.

`maintenance` 앱(모델 없음)이 `post_delete`·`pre_save` 시그널로 처리한다.

**왜 앱별로 흩지 않았나.** "레코드가 사라지면 파일도 사라진다"는 앱별 규칙이
아니라 프로젝트 전체 정책이다. 앱마다 흩어 두면 다섯 번째 `FileField` 를
추가하는 사람이 이 규칙을 모른 채 넘어가고 그 앱만 조용히 샌다. 그래서
프로젝트 안(BASE_DIR 하위) 모델을 훑어 `FileField` 를 **자동으로** 찾는다.
앱 라벨을 손으로 적었다면 그 목록이 낡는 순간 같은 문제가 재발한다.

**겪은 함정 — `weak=False`.** 처음에는 시그널이 **조용히 아무 일도 하지
않았다.** 에러도 경고도 없었다. Django 시그널은 기본이 약한 참조인데,
`_make_*()` 가 만들어 넘기는 클로저는 다른 곳에서 참조하지 않아
`connect()` 직후 GC 된다. 팩토리 함수로 핸들러를 만드는 구조에서는
`weak=False` 가 필수다.

**안전장치 셋:**

| 장치 | 없으면 |
|---|---|
| `transaction.on_commit()` 이후에만 삭제 | 롤백된 삭제가 파일을 날린다. 레코드는 살아 돌아오는데 파일은 안 돌아온다 |
| 같은 파일명을 다른 레코드가 참조하면 유지 | 남은 레코드의 파일이 통째로 사라진다 |
| 삭제 실패는 로그만 남기고 통과 | 정리 실패가 사용자의 삭제 요청을 500 으로 만든다 |

**이미 쌓인 것**은 `cleanup_orphan_files` 로 회수한다. **기본이 조회 전용**
이다 — 지운 파일은 되돌릴 수 없으니 무엇이 지워질지 먼저 보게 한다.
`--min-age-hours`(기본 24)는 업로드가 "파일 먼저, 레코드 나중" 순서라
그 사이에 도는 명령이 방금 올라온 파일을 고아로 오인하는 것을 막는다.

**대가.** 파일 삭제가 되돌릴 수 없다. 실수로 레코드를 지우면 예전에는
파일이라도 남았지만 이제는 함께 사라진다. 백업(11-5 · 10절)이 그만큼 더
중요해졌다. 주간 자동 정리 타이머는 **선택**으로 두었다 — 시그널이 제
역할을 하면 지울 것이 없어서, 자동 삭제를 굳이 켤 이유가 크지 않다.

## 남겨둔 위험

배포 시점(2026-08-26)에 적어 둔 셋은 모두 처리했다.

| 위험 | 상태 |
|---|---|
| 동적 IP | ✅ 결정 10 · Cloudflare DDNS (5분 주기) |
| rate limit 없음 | ✅ 결정 9 |
| 재색인이 동기 | ✅ 결정 8 |

지금 남은 것:

- **DDNS 반영에 시차가 있다.** IP 가 바뀐 뒤 최대 5분 + DNS TTL(자동 =
  300초)만큼 옛 주소를 가리킨다. 주기를 줄여도 TTL 이 하한이라 실익이 적다.
- **하루 한도가 계정 단위다.** 계정을 여러 개 만들면 우회된다. 가입 자체에
  제한(이메일 인증 등)이 없기 때문인데, 그건 별개 결정이다.
- **임베딩 캐시가 무한히 자란다.** `vector_db/embedding_cache.json` 이 이미
  27MB 다. 문서를 지워도 그 텍스트의 캐시 항목은 남는다. 재색인 비용을
  아끼는 장치라 당장 문제는 아니지만, 언젠가 정리 기준이 필요하다.
  (업로드 파일 쪽은 결정 11 로 해소했다 — 이건 별개다)
